# CI/CD Pipeline — Design

**Status:** Approved
**Date:** 2026-08-08
**Scope:** Second of four remaining sub-projects (CI/CD, on-call diagnostic agent, chaos-driven eval harness, Kubernetes migration), following Grafana dashboards + alerting. This spec covers CI/CD only.

## Problem

There is no automated testing or build verification on this repository at all — no `.github/workflows/`, no lint tooling, no branch protection. Every one of this project's real bugs (documented extensively in `learn.md` and `README.md`'s "Fixed this session" history) was found by a human running `pytest` or the live cluster manually. There is currently one unmerged feature branch (`worktree-grafana-dashboards-alerting`) with no automated check protecting `main` from a bad merge, and every future feature branch (the diagnostic agent, the eval harness, the Kubernetes migration) will be in the same position unless this is fixed first.

## Goals

- Every push and every PR against `main` automatically runs the full test suite and a linter.
- The Docker image is verified to still build on every push/PR, and published to a registry on merges to `main`.
- `main` can be configured (one-time, manual) to require these checks before merging.

## Non-goals

- Deployment automation (this is Docker Compose only, per the existing project — no CD to a live environment; the Kubernetes migration, a separate future sub-project, may revisit this).
- A pre-commit hook or local lint-on-save setup — CI-only for v1.
- Fixing every possible lint category ruff supports — only ruff's sane default rule set (`E4`, `E7`, `E9`, `F` — pyflakes plus basic pycodestyle checks), not an expanded/opinionated rule set.

## Architecture

One workflow file, `.github/workflows/ci.yml`, with three jobs:

```
push (any branch) ─┐
                    ├─→ test ──────┐
pull_request(main)─┘              ├─→ needs: [test, lint] ─→ docker-build-push
                    └─→ lint ──────┘        (main only)
```

`test` and `lint` run in parallel — they're independent of each other. `docker-build-push` depends on both (`needs: [test, lint]`), so a broken build or a lint failure never results in a published image. `docker-build-push` only actually pushes on `push` events targeting `main` (not on PRs or feature-branch pushes) — no point publishing an image for in-progress work.

## `test` job

- Checkout, `actions/setup-python@v5` pinned to Python 3.11 — matches the pinned `grpcio==1.59.0` in `requirements.txt`, which has no prebuilt wheel for Python 3.13+ (the same constraint already documented in README's "Local Development Setup").
- `pip install -r requirements.txt`
- `bash scripts/gen_protos.sh` — regenerate the protobuf stubs with the pinned `grpcio-tools` toolchain, exactly as local dev setup does (the committed `_pb2.py` files can go stale if generated with a different protoc version — this project has hit that exact bug before, per README).
- `PYTHONPATH=. pytest tests/ -v`

## `lint` job

No linter exists anywhere in this repo today. This feature adds one: **ruff**, chosen for being a single fast tool covering both linting and import-sort checking with minimal config, rather than assembling flake8 + isort + separate configs.

Verified against the current codebase (not assumed): ruff's **default** rule set (`E4`, `E7`, `E9`, `F`) finds **49 violations** today — unused imports, unused variables, and two `== False`/`== True` comparisons. 2 of the 49 are in generated protobuf files (`raft/proto/raft_pb2.py`, `client/proto/client_pb2.py`), which get **excluded from linting entirely** (`*_pb2.py`, `*_pb2_grpc.py` in `ruff.toml`'s `exclude`) — they're regenerated by `scripts/gen_protos.sh`, hand-fixing generated code is pointless and any fix would be lost on the next regen. The remaining ~47 real violations, spread across `raft/`, `kv/`, `server/`, `scripts/`, and `tests/`, are fixed as part of this feature — **lint starts clean and blocking from day one**, with no baseline-ignore file and no grandfathered debt.

Explicitly **not** adopting ruff's expanded/opinionated rule categories (pyupgrade, flake8-bandit, pylint-equivalent, etc.) for v1 — those surfaced 303 violations in a preview run, most of them stylistic opinions (blind `except:`, deprecated typing syntax) rather than real bugs, and adopting them is a separate, much larger decision than "add basic lint checking."

- Checkout, setup Python 3.11 (same as `test`, for consistency, though ruff itself isn't Python-version-sensitive)
- `pip install ruff` (added to `requirements.txt`)
- `ruff check .`

## `docker-build-push` job

- `needs: [test, lint]`
- Checkout, `docker/build-push-action` builds `ops/Dockerfile`
- On `push` to `main` only: authenticate to GHCR using the automatic `GITHUB_TOKEN` (no secrets to create or manage — this is why GHCR was chosen over Docker Hub, which would require creating a Docker Hub account and adding `DOCKERHUB_USERNAME`/`DOCKERHUB_TOKEN` as repo secrets), push `ghcr.io/angelali03/raft-node:latest` and `ghcr.io/angelali03/raft-node:<git-sha>`.
- On PRs / non-main branches: build only (`docker build`, no push) — verifies the Dockerfile still builds without publishing anything.

## Branch protection (manual, documented — not automatable here)

"Gates merges on green" requires GitHub's branch protection ("require status checks to pass before merging"), which is a repository *setting*, not something a workflow YAML file can configure itself. This environment has no `gh` CLI access to set it via API either. This feature adds a short README section with the exact one-time manual steps:

1. GitHub repo → Settings → Branches → Add branch protection rule
2. Branch name pattern: `main`
3. Enable "Require status checks to pass before merging"
4. Select `test` and `lint` as required checks
5. Save

## File layout

```
.github/
  workflows/
    ci.yml          # the three-job workflow described above
ruff.toml            # pins the E4/E7/E9/F rule set, excludes *_pb2.py/*_pb2_grpc.py
requirements.txt      # gains: ruff
```

Plus fixes to the ~47 real lint violations across existing `raft/`, `kv/`, `server/`, `scripts/`, `tests/` files (mechanical — unused imports/variables, `== False`/`== True` comparisons), and a new "Continuous Integration" section in README.md documenting the workflow and the manual branch-protection steps.

## Verification plan

1. Push this branch and confirm the `test`, `lint`, and `docker-build-push` (build-only) jobs all appear and pass in GitHub's Actions tab — not just "the YAML is syntactically valid," but an actual real run.
2. Deliberately break something in a scratch commit (e.g. reintroduce an unused import) on the branch, push, confirm `lint` actually fails red — then revert and confirm it goes green again. Same check for `test` (temporarily break an assertion).
3. Merge to `main`, confirm `docker-build-push` actually pushes an image, and confirm it's visible at `ghcr.io/angelali03/raft-node`.
4. Manually enable branch protection per the documented steps, then confirm (e.g. via a throwaway PR) that GitHub actually blocks merging until checks pass.
5. Full existing test suite (165 tests) still green — this feature must not change any test behavior, only add infrastructure around running them.

## Rollout / git hygiene

Follows this repo's standing convention: implementation code (`.github/`, `ruff.toml`, `requirements.txt`, the lint fixes, README updates) gets committed and pushed; nothing is committed without explicit go-ahead. Given this feature's entire point is exercising GitHub Actions, it needs an actual push to a real branch to verify (Actions don't run on purely local commits) — this will be flagged explicitly when reached, since pushing is a more visible action than the local-only work done so far this session.
