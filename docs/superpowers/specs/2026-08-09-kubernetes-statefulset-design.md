# Kubernetes StatefulSet Migration — Design

**Status:** Approved
**Date:** 2026-08-09
**Scope:** Third of the remaining sub-projects (after Grafana dashboards + alerting, and the CI/CD pipeline — both now built, merged, and live-verified). This spec covers the Kubernetes migration only. The originally-planned "on-call diagnostic agent" and "chaos-driven eval harness" sub-projects are deferred indefinitely and are not part of this or any currently-planned work.

## Problem

The cluster runs only on Docker Compose (`ops/docker-compose.yml`, generated by `scripts/gen_docker_compose.py`). That's fine for local development, but it means the project can't demonstrate the deployment concerns that actually matter for a consensus system in production:

- **Stable identity across restarts.** Compose gives this incidentally (fixed service names + named volumes), but nothing in the setup *enforces* that a restarted node reattaches its own durable state.
- **Quorum-preserving rollouts.** Nothing currently prevents a deploy from taking down more than a minority of nodes at once. For a Raft cluster, that's not a performance problem — it's a total loss of availability, and the deployment layer is the only place that constraint can be expressed.
- **Meaningful readiness.** The existing `/health` endpoint (`server/metrics_server.py`) returns `"OK"` unconditionally, regardless of Raft state. It's a fine liveness check; it is not a readiness signal.

## Goals

- Run the cluster on Kubernetes as a StatefulSet with stable per-pod identity and per-pod persistent volumes.
- Encode Raft's quorum requirement into a PodDisruptionBudget so rolling updates and node drains provably cannot break consensus.
- Add a real readiness probe that reflects actual Raft state, distinct from the existing liveness check.
- Verify all of the above live against a real local Kubernetes cluster — not by inspecting YAML.

## Non-goals

Each of these is a deliberate exclusion, not an oversight:

- **No Helm chart.** Raw manifests plus a generator script, matching the project's existing `gen_docker_compose.py` pattern. Helm would add a templating language to learn on top of the k8s concepts this feature exists to demonstrate.
- **No cloud deployment.** Local `kind` cluster only. Cloud adds credentials, cost, and a registry story without exercising anything new about the Raft/k8s interaction.
- **No Ingress.** A ClusterIP Service plus `kubectl port-forward` is sufficient for the client API at this stage.
- **No HorizontalPodAutoscaler.** Autoscaling a Raft cluster is actively wrong, not merely unimplemented: changing cluster membership requires Raft's joint-consensus / membership-change protocol (§6 of the paper), which this project does not implement. Scaling replicas up or down without it would silently break the quorum math. Worth stating explicitly so its absence reads as a decision.
- **Docker Compose is not replaced.** It remains fully supported and documented. Both deployment paths coexist; the k8s path is additive.
- **No dynamic peer discovery.** See "Peer discovery" below — this is a considered choice, not a shortcut.

## Local Kubernetes environment

`kubectl` is already installed; no cluster tool is. This feature installs and uses **kind** (Kubernetes-in-Docker): lightest of the options, runs as Docker containers on the existing Docker install, fast to create and destroy, and the conventional choice for exactly this kind of local StatefulSet testing.

**Node count for local verification: 5**, not 15. `--nodes N` stays parametric (mirroring `gen_docker_compose.py`, which defaults to 15 and supports any N), but 15 pods each with a PVC on a local kind cluster is slow to iterate against. Quorum for N=5 is 3, which exercises the PDB math identically to N=15/quorum=8.

## Architecture

New `ops/k8s/` directory containing generated manifests, produced by a new `scripts/gen_k8s_manifests.py --nodes N`. Generated rather than hand-written for the same reason the Compose file is: hand-maintaining N near-identical blocks is precisely how the port and peer-list mistakes documented in this project's own history crept in.

Five manifests:

1. **StatefulSet** — N replicas, stable pod names (`raft-node-0` … `raft-node-{N-1}`), `volumeClaimTemplates` giving each pod its own PVC mounted at `/app/data` (the k8s equivalent of Compose's per-node named volumes), liveness and readiness probes, and the generated peer list injected via ConfigMap.
2. **Headless Service** (`clusterIP: None`) — what gives StatefulSet pods individually-resolvable DNS names (`raft-node-0.raft.default.svc.cluster.local`). Required for stable network identity; without it, pods are only reachable through a load-balanced VIP, which is useless for peer-to-peer consensus traffic.
3. **ClusterIP Service** — a single stable address over the client port, so `kvctl` has one endpoint rather than needing to pick a pod.
4. **PodDisruptionBudget** — `minAvailable: (N // 2) + 1`, i.e. the quorum count. This is the manifest that encodes Raft's safety requirement into the deployment layer.
5. **ConfigMap** — holds the generated peer list.

## Peer discovery: static, generated at manifest-creation time

StatefulSet pod names are deterministic and knowable ahead of time (`raft-node-0`, `raft-node-1`, …), exactly like Compose service names. So peer discovery stays static: the generator computes the full peer list and bakes it into a ConfigMap. No runtime discovery mechanism (k8s API queries, DNS SRV lookups) is introduced — that would be a substantially larger change to the startup path in exchange for capability this deployment model doesn't need.

**The existing peer-list format does not change.** `parse_peer_list()` in `server/cluster_boot.py` already accepts `node_id:host:raft_port:client_port`, which expresses k8s addressing fine:

```
raft-node-0:raft-node-0.raft:50051:51051,raft-node-1:raft-node-1.raft:50051:51051,...
```

Note the shape difference from Compose: under Compose, every node has a *unique port* and the host is the service name. Under a StatefulSet, every pod uses the *same ports* and differs by *hostname*. The existing parser handles both without modification.

### The one real code change: `NODE_ID` derivation

Compose sets `NODE_ID` explicitly per service, because each service is its own spec. A StatefulSet's pods all share a single pod template, so `NODE_ID` cannot be hardcoded — each pod must derive its own identity at startup from the Kubernetes downward API (`metadata.name`, which is `raft-node-0` etc.).

This is a small, contained change in `get_cluster_config()` (`server/cluster_boot.py`): continue to honor an explicit `NODE_ID` when set (preserving the Compose path exactly), and fall back to the pod name supplied via the downward API when it isn't.

## Readiness probe

Add a `/ready` endpoint to `server/metrics_server.py`, alongside the existing `/health`, which stays unchanged as the liveness probe.

- **Liveness** (`/health`) — "is this process alive." Unconditional `OK`, as today.
- **Readiness** (`/ready`) — "should this pod receive traffic." Returns 200 once the node has a settled role (FOLLOWER or LEADER) with a known term; 503 during the startup window before the first election resolves.

This matches Raft's actual availability model: a settled follower can serve reads and a leader can serve writes, but a node that hasn't yet learned who the leader is has nothing useful to offer. Deliberately *not* implementing the stricter "ready only if commit_index is caught up" variant — that requires knowing the cluster's true commit_index for comparison, which is a meaningfully harder problem and not needed for this feature's goals.

`MetricsServer` currently only holds a reference to the Prometheus registry and has no view of Raft state, so it will need a reference to the `RaftNode` (or a small state-reading callback) wired in where it's constructed.

## Verification plan

Live verification against a real kind cluster. Steps 5 and 6 are the ones that matter — the rest is setup that makes them possible.

1. **Install kind, create a cluster, load the image.** `kind load docker-image raft-node:latest` is required: kind's nodes cannot pull from the host Docker daemon, so the image must be explicitly loaded. (Skipping this produces `ImagePullBackOff` — worth hitting knowingly rather than debugging blind.)
2. **Apply manifests; confirm all N pods reach `Running` and `Ready`** — and specifically that readiness *lags* startup by a beat, which proves the new `/ready` probe reflects election state rather than always returning OK (the exact failure mode of the existing `/health`).
3. **Confirm a single leader is elected**, via `kubectl exec` + `kvctl cluster-info` — the same check used for the Compose path.
4. **Write through the leader, read back from a different pod** — proves replication works over pod DNS, not merely that pods are running.
5. **Stable identity across restart.** `kubectl delete pod raft-node-2`; confirm it returns as *the same* `raft-node-2`, reattaches *the same* PVC, and recovers its prior Raft state (log and term intact, not a fresh node). This is the entire distinction between a StatefulSet and a Deployment, and it directly exercises the crash-recovery path already built and tested in this project.
6. **PDB enforcement — the central check.** Trigger a rolling restart (`kubectl rollout restart statefulset/raft-node`) and confirm Kubernetes never takes down more than `N - quorum` pods simultaneously, with the cluster continuing to serve writes throughout. Then deliberately attempt to violate it (`kubectl drain` a node, or evict enough pods at once) and confirm the PDB actually *blocks* the eviction. A PodDisruptionBudget that has never been tested against a real eviction attempt is just a YAML file that looks correct.
7. **Full `pytest` suite still green** (169 tests). The `cluster_boot.py` and `metrics_server.py` changes must not regress the Compose path, which remains fully supported.

## Documentation (required, after implementation and verification)

This project's established convention is that every feature updates the four Markdown documents, with real findings rather than a restatement of the plan. This work is not complete until they are updated:

- **`README.md`** — a "Running on Kubernetes" section (kind setup, generating manifests, applying, verifying, tearing down) parallel to the existing "Running the Cluster" section; the Project Structure tree updated with `ops/k8s/` and `scripts/gen_k8s_manifests.py`; any new entries in "Fixed this session" for bugs found during live verification; and the Kubernetes item removed from the Future Roadmap.
- **`learn.md`** — a new Part covering the Compose→Kubernetes progression: why StatefulSet rather than Deployment, what headless Services actually do and why peer-to-peer traffic requires them, how `volumeClaimTemplates` map to per-node durable state, why a PDB is the deployment-layer expression of Raft's quorum rule, and the liveness-vs-readiness distinction. Plus any new "Bugs We Hit" entries in the existing Part 6 numbering.
- **`INTERVIEW_GUIDE.md`** — a Kubernetes deployment section and at least one new Q&A (the PDB/quorum relationship is the strongest talking point here).
- **`QUICK_REFERENCE.md`** — a Kubernetes section and a corresponding short Q&A.

Every bug found during live verification gets documented with root cause and fix, per the convention visible throughout the existing "Fixed this session" list and `learn.md`'s Part 6 — not just the successes.

## Rollout / git hygiene

Follows this repo's established convention: work happens on an isolated worktree/branch, never directly on `main`. Nothing is pushed without explicit go-ahead. CI (`test` + `lint`, now required on `main`) must pass before merge; note that the new manifests and generator will be linted by ruff like any other Python, and the generated YAML is not executed by CI (no k8s cluster in the CI environment) — verification is local and manual by design.
